# BÁO CÁO KỸ THUẬT: TRIỂN KHAI VÀ VẬN HÀNH HỆ THỐNG PHARMACY POS

## CHƯƠNG 1: TỔNG QUAN HỆ THỐNG PHARMACY POS

### 1.1. Giới thiệu bài toán và hệ thống
Trong kỷ nguyên chuyển đổi số và tối ưu hóa vận hành, ngành bán lẻ dược phẩm đòi hỏi các hệ thống quản lý điểm bán hàng (POS - Point of Sale) phải đảm bảo tính chính xác tuyệt đối, thời gian phản hồi thời gian thực (Real-time) và quy trình vận hành khép kín từ khâu quản lý kho, lô hàng, hạn sử dụng cho đến tương tác bán hàng trực tiếp. Hệ thống Quản lý Nhà thuốc chuyên nghiệp (dự án Hệ thống Dược An Khang) được nghiên cứu và phát triển nhằm giải quyết triệt để các thách thức trên thông qua việc tối ưu hóa quy trình nghiệp vụ bán thuốc, kiểm soát chặt chẽ thông tin khách hàng, nhân viên và các giao dịch hóa đơn.

Tuy nhiên, việc triển khai một hệ thống phần mềm đa tầng trong môi trường doanh nghiệp thường gặp phải các rào cản lớn liên quan đến sự bất đồng nhất giữa môi trường phát triển cục bộ của lập trình viên và môi trường vận hành thực tế của máy chủ. Những xung đột về phiên bản hệ điều hành, thư viện phụ thuộc (dependencies), hay cấu hình mạng nội bộ thường dẫn đến lỗi hệ thống khi nâng cấp hoặc mở rộng.

Để giải quyết triệt để bài toán này, giải pháp Docker hóa (Containerization) toàn bộ hệ thống đã được áp dụng. Bằng cách đóng gói toàn bộ mã nguồn cùng môi trường thực thi cần thiết vào các Container độc lập, dự án đảm bảo tính đồng nhất tuyệt đối khi vận hành, giảm thiểu tối đa thời gian triển khai (Deployment time), đồng thời tăng cường khả năng cô lập bảo mật giữa các phân vùng dữ liệu và nghiệp vụ.

### 1.2. Kiến trúc tổng thể (3-Tier Architecture)
Hệ thống Dược An Khang được thiết kế vững chắc dựa trên Kiến trúc 3 tầng chuẩn (3-Tier Architecture) hoạt động hoàn toàn trong môi trường được đóng gói bằng Docker. Việc phân tách rõ ràng giữa các tầng giao diện, xử lý nghiệp vụ và lưu trữ dữ liệu giúp nâng cao tính bảo trì, tính cô lập lỗi và khả năng mở rộng độc lập của từng thành phần.

*   **Tầng Giao Diện (Frontend - Presentation Tier):**
    *   **Công nghệ cốt lõi:** Xây dựng trên nền tảng thư viện ReactJS hiện đại kết hợp với Vite làm công cụ đóng gói và biên dịch (Build tool) tốc độ cao, tối ưu hóa giao diện người dùng bằng TailwindCSS.
    *   **Máy chủ Web và Điều phối:** Sử dụng một Container Nginx làm máy chủ phục vụ toàn bộ các tệp tin tĩnh (Static files) sau khi biên dịch. Đồng thời, Nginx đóng vai trò là một Reverse Proxy chịu trách nhiệm đón nhận mọi yêu cầu (requests) gọi sang tầng Backend, giúp che giấu cấu trúc mạng nội bộ bên trong.
*   **Tầng Nghiệp Vụ (Backend - Application Tier):**
    *   **Công nghệ cốt lõi:** Sử dụng Framework Java Spring Boot, tối ưu hóa việc quản lý thư viện và vòng đời dự án thông qua Maven.
    *   **Môi trường thực thi (Runtime):** Hệ thống sử dụng Java 17 (Eclipse Temurin JRE) làm nền tảng chạy mã nguồn, đảm bảo hiệu năng xử lý đa luồng mạnh mẽ, an toàn và tối ưu hóa tài nguyên phần cứng máy chủ.
*   **Tầng Cơ Sở Dữ Liệu (Database - Data Tier):**
    *   **Công nghệ cốt lõi:** Hệ quản trị cơ sở dữ liệu NoSQL MongoDB phiên bản 8.0. Sự lựa chọn này đáp ứng hoàn hảo khả năng lưu trữ linh hoạt các cấu trúc dữ liệu bán hàng phức tạp, không định hình (như thông tin chi tiết hóa đơn, danh mục thuốc với nhiều thuộc tính thay đổi liên tục) và cung cấp tốc độ truy vấn cao.

### 1.3. Mô hình điều phối và Đóng gói (Containerization)
Toàn bộ kiến trúc 3 tầng trên được ảo hóa và quản lý tập trung thông qua Docker Engine và công cụ điều phối mạng Docker Compose.

Thay vì cài đặt trực tiếp các phần mềm nền tảng lên hệ điều hành của máy chủ vật lý (Host Machine), từng thành phần (Nginx Frontend, Spring Boot Backend, MongoDB Database) sẽ được cô lập trong một "hộp chứa" Container riêng biệt. Docker Compose đóng vai trò là kiến trúc sư trưởng đọc các bản vẽ cấu hình cấu trúc mạng ảo nội bộ, thiết lập cơ chế kiểm tra trạng thái sức khỏe dịch vụ (Healthcheck) và gắn kết các vùng đĩa ảo bền vững (Volumes). Điều này giúp toàn bộ hệ thống Pharmacy có khả năng khởi dựng tức thì chỉ bằng một câu lệnh duy nhất, loại bỏ hoàn toàn các lỗi phát sinh do sai lệch môi trường hệ thống.

## CHƯƠNG 2: CẤU TRÚC THƯ MỤC DỰ ÁN & QUY HOẠCH MÃ NGUỒN

### 2.1. Sơ đồ cây thư mục toàn diện (Project Structure)
Để quản lý mã nguồn hiệu quả trong mô hình kiến trúc đa tầng (3-Tier Architecture) chạy trên nền tảng Docker, cấu trúc thư mục của dự án Pharmacy Project (Hệ thống Dược An Khang) được tổ chức phân tách rõ ràng thành các phân vùng độc lập. Dưới đây là sơ đồ cây thư mục toàn diện của dự án, thể hiện vị trí của mã nguồn Frontend, Backend cùng các tệp tin cấu hình Docker, biến môi trường và script vận hành hệ thống:

```text
pharmacy-project/
├── .env.example                # File môi trường mẫu (không chứa các key nhạy cảm)
├── docker-compose.yml          # File Docker Compose gốc (định nghĩa services, networks và volumes)
├── docker-compose.dev.yml      # File Docker Compose ghi đè cho môi trường Phát triển (Development)
├── docker-compose.prod.yml     # File Docker Compose ghi đè cho môi trường Vận hành (Production)
├── import_db.sh                # Script Bash nạp dữ liệu mẫu vào MongoDB container
├── README.md                   # Hướng dẫn tổng quan dự án
├── backend/                    # Mã nguồn tầng Backend (Java Spring Boot)
│   ├── pom.xml                 # File quản lý dependencies của Maven
│   ├── Dockerfile              # File cấu hình Docker image cho Backend (Multi-stage)
│   ├── src/                    # Thư mục chứa mã nguồn Java
│   │   ├── main/               # Mã nguồn logic xử lý nghiệp vụ chính
│   │   └── test/               # Các kịch bản kiểm thử (Unit test)
│   └── target/                 # Thư mục build output (.jar) (bị bỏ qua khi push)
├── frontend/                   # Mã nguồn tầng Frontend (ReactJS + Vite)
│   ├── package.json            # File khai báo dependencies và scripts của Node.js
│   ├── Dockerfile              # File cấu hình Docker image cho Frontend (Multi-stage)
│   ├── nginx.conf              # File cấu hình Nginx (Routing SPA và Reverse Proxy)
│   ├── vite.config.js          # File cấu hình Vite build tool
│   ├── tailwind.config.js      # File cấu hình TailwindCSS
│   ├── index.html              # Điểm nhập giao diện HTML chính
│   └── src/                    # Thư mục chứa mã nguồn component và logic React
└── json_data/                  # Dữ liệu JSON mẫu phục vụ việc import ban đầu
    ├── employees.json          # Dữ liệu mẫu phân hệ Nhân viên
    ├── products.json           # Dữ liệu mẫu danh mục Thuốc/Sản phẩm
    ├── customers.json          # Dữ liệu mẫu phân hệ Khách hàng
    └── invoices.json           # Dữ liệu mẫu phân hệ Hóa đơn giao dịch
```

### 2.2. Định nghĩa chi tiết chức năng các thành phần
Sự phân tách thư mục như sơ đồ trên tuân thủ nghiêm ngặt nguyên tắc cô lập cấu phần. Dưới đây là giải thích chi tiết vai trò của các file cấu hình tại thư mục gốc và các module thành phần:

#### 2.2.1. Phân tích các file cấu hình cốt lõi tại thư mục Root

| Tên File | Vai trò / Chức năng |
| :--- | :--- |
| **`.env.example`** | Bản mẫu (template) khai báo danh sách toàn bộ biến môi trường mà hệ thống cần. File này không chứa mật khẩu hay chuỗi kết nối thực tế để đảm bảo an toàn khi chia sẻ mã nguồn. |
| **`docker-compose.yml`** | Bản vẽ kiến trúc nền tảng định nghĩa bộ khung cốt lõi gồm 3 dịch vụ chính (`frontend`, `spring-boot`, `mongodb`), cấu hình liên kết mạng ảo (`networks`) và phân vùng lưu trữ lâu dài (`volumes`). |
| **`docker-compose.dev.yml`**<br>**`docker-compose.prod.yml`** | Các tệp cấu hình bổ sung áp dụng kỹ thuật **Kế thừa & Ghi đè (Override)** của Docker Compose. Chúng chứa các thiết lập đặc thù cho từng môi trường (như mở cổng debug ở Dev hoặc thắt tài nguyên, cấu hình SSL ở Prod) mà không làm lặp lại cấu hình chung. |
| **`import_db.sh`** | Tập lệnh tự động hóa (Bash script) tương tác trực tiếp với container cơ sở dữ liệu để nạp nhanh toàn bộ kho dữ liệu JSON mẫu vào MongoDB engine, giúp thiết lập môi trường chạy thử nghiệm chỉ trong vài giây. |

#### 2.2.2. Quy hoạch cấu trúc các thư mục Module Con

| Thư mục | Vai trò / Chức năng |
| :--- | :--- |
| **`backend/`** | Tập trung toàn bộ logic xử lý nghiệp vụ của nhà thuốc. Tệp `pom.xml` quản lý tập trung các thư viện phụ thuộc của Spring Boot. Mã nguồn được bảo vệ và tối ưu hóa đóng gói thông qua một tệp `Dockerfile` đa tầng riêng biệt nhằm tạo ra các bản build siêu nhẹ. |
| **`frontend/`** | Quản lý toàn bộ mã nguồn giao diện tương tác của người dùng. Ngoài mã nguồn ReactJS, thư mục này tích hợp sẵn tệp cấu hình `nginx.conf` độc lập. Khi build image cho Frontend, tệp tin này sẽ được nhúng thẳng vào container Nginx để định tuyến ứng dụng trang đơn (SPA) và làm cổng kết nối API an toàn. |
| **`json_data/`** | Lưu trữ cấu trúc dữ liệu thô ban đầu dưới dạng các mảng đối tượng JSON (nhân viên, khách hàng, thuốc, hóa đơn). Cấu trúc này được đồng bộ chuẩn hóa với các Entity mô hình hóa trong Java Spring Boot và cơ sở dữ liệu MongoDB, giúp hệ thống sẵn sàng hoạt động ngay sau khi khởi dựng. |

## CHƯƠNG 3: CHI TIẾT CẤU HÌNH ĐÓNG GÓI CONTAINER (DOCKERFILE & SERVICE CONFIG)

Để tối ưu hóa dung lượng lưu trữ, tăng tốc độ triển khai và nâng cao tính an toàn bảo mật cho hệ thống Pharmacy, mã nguồn của cả hai phân hệ Frontend và Backend đều áp dụng nghiêm ngặt phương pháp **Multi-stage Build (Xây dựng đa tầng)** trong cấu hình Dockerfile. Phương pháp này tách biệt hoàn toàn môi trường biên dịch mã nguồn (nặng nề, chứa nhiều công cụ phát triển) ra khỏi môi trường vận hành runtime cuối cùng (siêu nhẹ, chỉ chứa các thành phần cốt lõi để chạy ứng dụng).

### 3.1. Cấu hình tầng Frontend
Dockerfile của Frontend chịu trách nhiệm chuyển hóa mã nguồn ReactJS + Vite từ dạng mã phát triển thành các tệp tin tối ưu tĩnh và phân phối chúng qua máy chủ web Nginx siêu nhẹ.

#### 3.1.1. Nội dung file cấu hình `frontend/Dockerfile`
```dockerfile
# Bước 1: Build mã nguồn React sử dụng Node.js
FROM node:20-alpine AS build
WORKDIR /app

# Copy package.json và package-lock.json để cài đặt dependencies trước (tối ưu cache Docker)
COPY package*.json ./
RUN npm install

# Copy toàn bộ mã nguồn frontend và build bản production
COPY . .
RUN npm run build

# Bước 2: Dùng Nginx để chạy bản build
FROM nginx:alpine

# Copy file cấu hình Nginx custom vào container
COPY nginx.conf /etc/nginx/conf.d/default.conf

# Copy thư mục build từ bước 1 vào thư mục chứa static files của Nginx
COPY --from=build /app/dist /usr/share/nginx/html

EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

#### 3.1.2. Giải thích chi tiết mã lệnh kỹ thuật
*   `FROM node:20-alpine AS build`: Khởi tạo giai đoạn một (Stage 1) sử dụng môi trường Node.js phiên bản 20 trên nền hệ điều hành Alpine Linux tối giản nhằm tiết kiệm tài nguyên. Giai đoạn này được đặt bí danh (alias) là `build` nhằm phục vụ việc tham chiếu dữ liệu ở giai đoạn sau.
*   `COPY package*.json ./` và `RUN npm install`: Sao chép các tệp định nghĩa thư viện phụ thuộc vào container trước khi chép toàn bộ mã nguồn. Quy trình tách biệt này giúp tận dụng tối đa cơ chế lưu bộ đệm lớp (layer cache) của Docker. Nếu danh sách thư viện trong `package.json` không thay đổi, Docker sẽ bỏ qua bước tải và cài đặt lại ở các lần build sau, giảm thời gian build từ vài phút xuống vài giây.
*   `RUN npm run build`: Tiến hành biên dịch toàn bộ mã nguồn ReactJS (JSX, ES6, CSS) thành các tệp tin tĩnh tối ưu hóa (gồm HTML, JS, CSS) và lưu trữ tập trung tại thư mục `/app/dist`.
*   `FROM nginx:alpine`: Khởi động giai đoạn hai (Stage 2) - môi trường chạy thực tế. Tại bước này, Docker sẽ loại bỏ hoàn toàn môi trường Node.js cồng kềnh cùng toàn bộ mã nguồn gốc ở Stage 1, chỉ giữ lại một image Nginx Alpine siêu nhẹ (dung lượng chỉ khoảng 20-30MB) làm nền tảng vận hành.
*   `COPY nginx.conf /etc/nginx/conf.d/default.conf`: Ghi đè tệp tin cấu hình mặc định của Nginx bằng file cấu hình tùy chỉnh (`nginx.conf`) của dự án để thiết lập các chính sách định tuyến SPA và cổng kết nối ngược (Reverse Proxy).
*   `COPY --from=build /app/dist /usr/share/nginx/html`: Lệnh chuyển giao tài nguyên giữa các stage. Docker trích xuất duy nhất thư mục sản phẩm tĩnh `/app/dist` từ giai đoạn build trước đó và dán vào thư mục phân phối tệp static công khai của Nginx (`/usr/share/nginx/html`).
*   `EXPOSE 80`: Khai báo cổng lắng nghe của container là cổng 80 (cổng HTTP tiêu chuẩn).
*   `CMD ["nginx", "-g", "daemon off;"]`: Chỉ thị khởi chạy Nginx dưới dạng một tiến trình chính ở chế độ foreground. Điều này đảm bảo container sẽ luôn duy trì trạng thái hoạt động liên tục; nếu tiến trình Nginx gặp sự cố dừng lại, container cũng sẽ tự động dừng theo để hệ thống ghi nhận lỗi.

### 3.2. Cấu hình tầng Backend
Tương tự như phân hệ giao diện, tầng nghiệp vụ Java Spring Boot cũng được đóng gói thông qua cơ chế Multi-stage Build nhằm cô lập triệt để quy trình quản lý dependencies của Maven và rút gọn dung lượng đĩa từ hàng Gigabyte xuống còn khoảng 150 Megabyte bằng cách loại bỏ bộ cài đặt JDK.

#### 3.2.1. Nội dung file cấu hình `backend/Dockerfile`
```dockerfile
# Stage 1: Biên dịch mã nguồn với Maven và JDK
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /build

COPY pom.xml .
RUN mvn dependency:go-offline -B

COPY src ./src
RUN mvn package -DskipTests -B

# Stage 2: Vận hành ứng dụng với JRE tối giản
FROM eclipse-temurin:17-jre
WORKDIR /app

COPY --from=builder /build/target/*.jar app.jar

EXPOSE 8081
ENTRYPOINT ["java", "-jar", "app.jar"]
```

#### 3.2.2. Giải thích chi tiết mã lệnh kỹ thuật
*   `FROM maven:3.9-eclipse-temurin-17 AS builder`: Khởi tạo giai đoạn biên dịch mã nguồn (Stage 1). Image gốc sử dụng công cụ quản lý Maven phiên bản 3.9 tích hợp sẵn bộ phát triển OpenJDK 17 phân phối bởi Eclipse Temurin, đặt tên định danh cho tầng này là `builder`.
*   `RUN mvn dependency:go-offline -B`: Ra lệnh cho Maven tải trước toàn bộ các tệp tin thư viện cấu thành (.jar) được khai báo trong `pom.xml` về kho lưu trữ nội bộ của container. Tham số `-B` (Batch-mode) được kích hoạt để tắt bớt các dòng nhật ký (logs) tải file rườm rà, giúp tiến trình build sạch sẽ và nhanh chóng hơn.
*   `RUN mvn package -DskipTests -B`: Thực hiện biên dịch toàn bộ các lớp mã nguồn Java và đóng gói chúng thành một tệp tin thực thi duy nhất dạng `.jar` nằm trong thư mục `target/`. Cờ `-DskipTests` được truyền vào nhằm bỏ qua việc chạy các kịch bản kiểm thử (unit tests) trong lúc đóng gói, giúp gia tăng tối đa tốc độ build phân phối.
*   `FROM eclipse-temurin:17-jre`: Khởi tạo giai đoạn runtime (Stage 2). Bằng việc chuyển sang cấu hình Java Runtime Environment (JRE) thuần túy và loại bỏ hoàn toàn bộ công cụ biên dịch JDK cùng Maven của Stage 1, hệ thống không chỉ tiết kiệm dung lượng đĩa tối đa mà còn gia tăng tính an toàn bảo mật do thu hẹp diện tích bề mặt tấn công.
*   `COPY --from=builder /build/target/*.jar app.jar`: Bản sao tệp tin thực thi sau cùng. Docker trích xuất duy nhất tệp tin `.jar` đã build thành công từ giai đoạn builder sang giai đoạn runtime mới và đổi tên ngắn gọn thành `app.jar`.
*   `EXPOSE 8081`: Khai báo cổng dịch vụ nội bộ của ứng dụng Spring Boot là 8081.
*   `ENTRYPOINT ["java", "-jar", "app.jar"]`: Cấu hình lệnh cố định không thể bị ghi đè khi container khởi động. Lệnh này kích hoạt máy ảo Java thực thi trực tiếp gói ứng dụng `app.jar`, chính thức đưa các dịch vụ nghiệp vụ của nhà thuốc vào trạng thái sẵn sàng phục vụ.

## CHƯƠNG 4: KIẾN TRÚC MẠNG CONTAINER VÀ ĐIỀU PHỐI ĐA MÔI TRƯỜNG

Để đảm bảo tính toàn vẹn dữ liệu, khả năng chịu tải và an toàn thông tin theo tiêu chuẩn doanh nghiệp, kiến trúc điều phối của hệ thống Pharmacy không chỉ đơn thuần là khởi chạy các container mà là một giải pháp quy hoạch mạng và quản lý cấu hình đa môi trường chặt chẽ.

### 4.1. Sơ đồ Kiến trúc & Luồng dữ liệu mạng nội bộ (Container Networks)

#### 4.1.1. Sơ đồ luồng dữ liệu tổng thể
> 📷 **[HÌNH 1]**: *Sơ đồ luồng dữ liệu & điều phối mạng container (Bao gồm các thành phần: Host Machine (Ubuntu Server), Docker Daemon, phân vùng mạng `frontend-net` và phân vùng mạng `backend-net`).*

#### 4.1.2. Phân tích thiết kế mạng an toàn (Network Isolation)
Thay vì đặt tất cả các dịch vụ vào chung một không gian mạng dẫn đến rủi ro lộ lọt thông tin, hệ thống quy hoạch thành hai phân vùng mạng ảo cô lập (Docker Bridge Networks) riêng biệt:
*   **Mạng Giao tiếp Ngoại vi (`frontend-net`):** Đây là vùng mạng trung gian kết nối giữa container `frontend` (Nginx) và container `spring-boot` (Backend). Nginx tiếp nhận các yêu cầu truy cập giao diện từ thiết bị client bên ngoài qua cổng được ánh xạ, sau đó định tuyến ngược (Reverse Proxy) các request có tiền tố `/api` đến cổng dịch vụ 8081 của Backend.
*   **Mạng Nghiệp vụ Nội bộ (`backend-net`):** Phân vùng mạng hoàn toàn đóng kín, chỉ thiết lập kết nối giữa container `spring-boot` và container `mongodb`. Tầng nghiệp vụ Backend tương tác với Database thông qua chuỗi kết nối (Connection String) bảo mật.

> [!IMPORTANT]
> **Ý nghĩa bảo mật cốt lõi:** Container `frontend` hoàn toàn không được phân quyền tham gia vào mạng `backend-net`. Kiến trúc cô lập này triệt tiêu nguy cơ tấn công leo thang: nếu kẻ tấn công chiếm quyền kiểm soát container Frontend từ Internet, chúng hoàn toàn bị chặn đứng, không thể quét cổng (port scanning) hay truy cập trực tiếp vào cơ sở dữ liệu MongoDB nằm ở vùng lõi.

#### 4.1.3. Cơ chế phân giải tên miền nội bộ (Service Discovery)
Hệ thống tận dụng cơ chế Embedded DNS Service tích hợp sẵn của Docker. Trong các file cấu hình cấu trúc, các dịch vụ không kết nối với nhau bằng địa chỉ IP tĩnh (vốn luôn thay đổi mỗi khi container khởi động lại) mà gọi nhau bằng chính **Tên Dịch vụ (Service Name)** được định nghĩa trong Docker Compose. Cụ thể:
*   Nginx chuyển tiếp API đến địa chỉ: `http://spring-boot:8081`.
*   Spring Boot kết nối Database qua URI: `mongodb://<username>:<password>@mongodb:27017/db_name`.
Docker Daemon sẽ tự động phân giải các tên dịch vụ `spring-boot` và `mongodb` thành địa chỉ IP nội bộ tương ứng trong mạng ảo một cách chính xác và theo thời gian thực.

### 4.2. Chiến lược Quản lý Đa môi trường (Development, UAT, Production)

#### 4.2.1. Thách thức vận hành và giải pháp lựa chọn
Một ứng dụng doanh nghiệp bắt buộc phải trải qua nhiều giai đoạn vận hành từ máy cá nhân của lập trình viên (Development), môi trường kiểm thử giả lập (UAT) cho đến máy chủ chạy thực tế (Production). Thay vì viết các file cấu hình độc lập gây trùng lặp mã nguồn, dự án áp dụng kỹ thuật **Kế thừa & Ghi đè (Multiple Compose Files)**. Hệ thống thiết lập một file nền tảng cốt lõi `docker-compose.yml` (base) định nghĩa khung xương cấu trúc, sau đó sử dụng các tệp tin ghi đè chuyên biệt cho từng môi trường.

#### 4.2.2. Ưu điểm kiến trúc
1.  **Tối ưu mã nguồn (Nguyên lý DRY - Don't Repeat Yourself):** Toàn bộ các cấu hình chung như tên service, volumes, networks được khai báo duy nhất một lần tại file base, loại bỏ hoàn toàn việc sao chép lặp lại code.
2.  **Linh hoạt và dễ bảo trì:** Lập trình viên hay quản trị viên chỉ cần viết ngắn gọn các thông số đặc thù môi trường trong file override. Khi cần nâng cấp phiên bản image hoặc thêm một dịch vụ mới, hệ thống chỉ cần cập nhật tại một nơi duy nhất ở file base.
3.  **Hỗ trợ tự động hóa (CI/CD):** Cú pháp gọi chuỗi file liên tiếp bằng cờ `-f` giúp các công cụ tự động hóa dễ dàng nhận diện và cấu hình deploy tự động sang các cụm server tương ứng.

### 4.3. Cơ chế Quản lý Biến môi trường cách ly (.env)
Dự án tuân thủ nghiêm ngặt nguyên tắc tách biệt giữa Luồng xử lý (Cấu hình YAML) và Thông tin định danh/Nhạy cảm (Mật khẩu, API Key, Tags phiên bản).
*   **Tệp tin khuôn mẫu `.env.example`:** Được cam kết lưu trữ công khai trên kho mã nguồn Git (GitHub/GitLab). File này chỉ chứa cấu trúc tên các biến trống để hướng dẫn các thành viên trong đội ngũ phát triển biết hệ thống cần những thông số nào để khởi dựng.
*   **Các file giá trị thực tế (`.env.dev`, `.env.prod`, `.env.uat`):** Chứa các chuỗi kết nối và mật khẩu quản trị Root tối cao thực tế tương ứng với từng môi trường. Các tệp tin này được đưa vào danh sách loại trừ `.gitignore` để tuyệt đối không đẩy lên internet, tránh rủi ro lộ lọt an ninh mạng, và được cấu hình trực tiếp thủ công trên đĩa cứng máy chủ hoặc truyền qua các biến bí mật của hệ thống deployment.

Khi chạy hệ thống, Docker Compose sẽ ưu tiên đọc file môi trường được chỉ định bằng tham số `--env-file`, giúp hệ thống Pharmacy vận hành trơn tru và an toàn tuyệt đối.

## CHƯƠNG 5: QUY HOẠCH CHI TIẾT CẤU TRÚC HOST MACHINE VÀ CONFIG NGINX

Để giải quyết triệt để sự lặp lại cấu hình và tối ưu hóa tài nguyên phần cứng, hệ thống quy hoạch chi tiết sơ đồ thư mục trên máy chủ vật lý/máy ảo (Host Machine), đồng thời tùy biến file cấu hình máy chủ Nginx kết hợp với tệp tin ghi đè docker-compose riêng biệt cho từng môi trường vận hành cụ thể.

### 5.1. Môi trường Phát triển Cục bộ (DEV - Local Machine)
Môi trường DEV tập trung vào sự linh hoạt, tốc độ hot-reload mã nguồn và khả năng kiểm tra trực quan luồng dữ liệu của lập trình viên.

#### 5.1.1. Sơ đồ thư mục trên máy Host (DEV)
Tại máy cục bộ, mã nguồn gốc được lưu giữ nguyên bản và ánh xạ trực tiếp vào container:
```text
/home/user/projects/pharmacy-project/   # Thư mục gốc dự án trên máy cá nhân
├── backend/                            # Chứa source code Java
├── frontend/                           # Chứa source code ReactJS
└── docker-compose.dev.yml              # File thực thi môi trường local
```

#### 5.1.2. Cấu hình Nginx DEV (`nginx.dev.conf`)
Cấu hình tập trung xử lý định tuyến SPA và chuyển tiếp API về localhost mà không cần mã hóa bảo mật phức tạp.
```nginx
server {
    listen 80;
    server_name localhost;

    location / {
        root /usr/share/nginx/html;
        index index.html index.htm;
        try_files $uri $uri/ /index.html; # Xử lý cơ chế Client-side Routing của React Router
    }

    location /api {
        proxy_pass http://spring-boot:8081; # Chuyển tiếp các request gọi API sang container Backend
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

#### 5.1.3. Cấu hình ghi đè trong `docker-compose.dev.yml`
```yaml
version: '3.8'
services:
  frontend:
    ports:
      - "8082:80" # Ánh xạ cổng 8082 trên máy Host vào cổng 80 của container để Dev truy cập
    environment:
      - NODE_ENV=development

  spring-boot:
    ports:
      - "8081:8081" # Mở cổng Backend để dễ dàng debug hoặc test qua Postman độc lập
    environment:
      - SPRING_PROFILES_ACTIVE=dev

  mongodb:
    ports:
      - "27017:27017" # Mở cổng DB để kết nối trực tiếp từ MongoDB Compass trên máy Host
```

### 5.2. Môi trường Kiểm thử Tích hợp (UAT - Staging VPS)
Môi trường UAT giả lập cấu trúc deploy thực tế bằng image đóng gói sẵn nhưng bổ sung lớp bảo mật giới hạn người truy cập thử nghiệm.

#### 5.2.1. Sơ đồ thư mục trên máy Host (UAT)
Hệ thống không chạy bằng code live mà tải image từ Registry, quy hoạch đĩa cứng thu gọn:
```text
/opt/pharmacy-uat/
├── .env.uat
├── nginx.uat.conf
└── docker-compose.uat.yml
```

#### 5.2.2. Cấu hình Nginx UAT (`nginx.uat.conf`)
Tích hợp thêm cơ chế xác thực cơ bản HTTP Basic Authentication để ngăn chặn người ngoài truy cập vào phân hệ đang thử nghiệm.
```nginx
server {
    listen 80;
    server_name uat.duocankhang.internal;

    location / {
        auth_basic "Môi trường kiểm thử UAT - Yêu cầu đăng nhập";
        auth_basic_user_file /etc/nginx/.htpasswd; # File chứa mật khẩu mã hóa truy cập thử nghiệm
        
        root /usr/share/nginx/html;
        index index.html index.htm;
        try_files $uri $uri/ /index.html;
    }

    location /api {
        proxy_pass http://spring-boot:8081;
        proxy_set_header Host $host;
    }
}
```

#### 5.2.3. Cấu hình ghi đè trong `docker-compose.uat.yml`
```yaml
version: '3.8'
services:
  frontend:
    ports:
      - "8080:80" # Sử dụng cổng tiêu chuẩn thử nghiệm 8080
    volumes:
      - ./nginx.uat.conf:/etc/nginx/conf.d/default.conf

  spring-boot:
    # Đóng cổng 8081 ngoại vi, chỉ cho phép nhận request đi vòng qua Nginx Frontend
    expose:
      - "8081"
    environment:
      - SPRING_PROFILES_ACTIVE=uat

  mongodb:
    # Không expose port 27017 ra ngoài internet để tránh quét cổng trên VPS
    expose:
      - "27017"
```

### 5.3. Môi trường Vận hành Chính thức (PRODUCTION - Live Server)
Môi trường tối cao, đặt tiêu chí Bảo mật tuyệt đối, Chứng chỉ mã hóa (SSL), Tiết kiệm và Kiểm soát cứng giới hạn tài nguyên (Resource limits) lên hàng đầu.

#### 5.3.1. Sơ đồ thư mục trên máy Host (PRODUCTION)
Tách biệt phân vùng lưu trữ lâu dài bền vững của Cơ sở dữ liệu ra một thư mục bảo mật riêng trên ổ đĩa SSD của Server:
```text
/app/pharmacy-prod/
├── .env.prod
├── nginx.prod.conf
├── docker-compose.prod.yml
└── ssl/
    ├── duocankhang.crt                 # Chứng chỉ SSL thương mại
    └── duocankhang.key                 # Khóa bí mật SSL
```

#### 5.3.2. Cấu hình Nginx Production (`nginx.prod.conf`)
Cấu hình bắt buộc chuyển hướng toàn bộ lưu lượng HTTP không an sau giao thức mã hóa HTTPS cổng 443.
```nginx
server {
    listen 80;
    server_name duocankhang.vn www.duocankhang.vn;
    return 301 https://$host$request_uri; # Tự động chuyển hướng (Redirect 301) sang HTTPS
}

server {
    listen 443 ssl;
    server_name duocankhang.vn www.duocankhang.vn;

    # Cấu hình chứng chỉ bảo mật SSL/TLS
    ssl_certificate /etc/nginx/ssl/duocankhang.crt;
    ssl_certificate_key /etc/nginx/ssl/duocankhang.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;

    location / {
        root /usr/share/nginx/html;
        index index.html index.htm;
        try_files $uri $uri/ /index.html;
    }

    location /api {
        proxy_pass http://spring-boot:8081;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https; # Khai báo giao thức mã hóa an toàn với Backend
    }
}
```

#### 5.3.3. Cấu hình ghi đè trong `docker-compose.prod.yml`
```yaml
version: '3.8'
services:
  frontend:
    ports:
      - "80:80"
      - "443:443" # Mở hai cổng mạng công khai tiêu chuẩn của Internet
    volumes:
      - ./nginx.prod.conf:/etc/nginx/conf.d/default.conf
      - ./ssl:/etc/nginx/ssl:ro # Mount chứng chỉ SSL ở chế độ Chỉ đọc (Read-Only) để bảo mật
    deploy:
      resources:
        limits:
          cpus: '0.50'     # Giới hạn tối đa sử dụng 50% cấu hình một lõi CPU
          memory: 256M    # Giới hạn tối đa dung lượng RAM cấp phát cho Nginx

  spring-boot:
    expose:
      - "8081"            # Giấu kín hoàn toàn port Backend khỏi Internet công cộng
    environment:
      - SPRING_PROFILES_ACTIVE=prod
    logging:
      driver: "json-file"
      options:
        max-size: "10m"   # Giới hạn file log tối đa 10 Megabyte
        max-file: "3"     # Lưu tối đa 3 file xoay vòng (Log rotation) để chống tràn ổ đĩa
    deploy:
      resources:
        limits:
          cpus: '1.50'    # Cấp tối đa 1.5 core CPU xử lý nghiệp vụ bán hàng
          memory: 768M    # Khống chế RAM tối đa 768MB nhằm ngăn ngừa sự cố Memory Leak rò rỉ bộ nhớ

  mongodb:
    expose:
      - "27017"           # Giấu kín port database, chỉ phản hồi truy vấn nội bộ từ Backend
    volumes:
      - /var/lib/pharmacy/mongodb-data:/data/db # Ánh xạ vùng lưu trữ dữ liệu thực tế vào SSD bảo mật của Host
    deploy:
      resources:
        limits:
          cpus: '2.0'     # Cấp tối đa 2 core CPU cho các tác vụ tính toán lập chỉ mục, truy vấn
          memory: 1G      # Khống chế cứng dung lượng RAM lưu đệm cho database tối đa 1 Gigabyte
```

## CHƯƠNG 6: HƯỚNG DẪN TRIỂN KHAI VÀ VẬN HÀNH CHI TIẾT THEO MÔI TRƯỜNG

Để đảm việc triển khai và vận hành được chuẩn hóa, quy trình của hệ thống Pharmacy (Dược An Khang) được phân tách thành 3 kịch bản môi trường độc lập. Quản trị viên và lập trình viên cần tuân thủ nghiêm ngặt các bước thực thi dưới đây.

### 6.1. PHẦN 1: HƯỚNG DẪN TRIỂN KHAI TRÊN MÔI TRƯỜNG PHÁT TRIỂN (DEV)
Môi trường DEV được triển khai ngay trên máy tính cá nhân (Local Machine) của lập trình viên, ưu tiên sự linh hoạt để phục vụ lập trình, sửa lỗi và debug nhanh.

*   **Bước 1: Khởi tạo tệp cấu hình môi trường Local**
    1.  Sao chép file khuôn mẫu sang file cấu hình thực tế cho môi trường phát triển:
        ```bash
        cp .env.example .env
        ```
    2.  Cấu hình file `.env` với các thẻ tag phiên bản phát triển và chuỗi kết nối mở cổng cục bộ (`MONGO_INITDB_ROOT_USERNAME=root`, `MONGO_INITDB_ROOT_PASSWORD=root`).
*   **Bước 2: Kích hoạt hệ thống DEV với mã nguồn trực tiếp**
    Thực hiện lệnh gộp file base và file override dev để Docker biên dịch trực tiếp mã nguồn từ thư mục `frontend/` và `backend/`:
    ```bash
    sudo docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build
    ```
    > 📷 **[HÌNH 2]**: *Ảnh chụp màn hình Terminal hiển thị các container môi trường DEV khởi chạy thành công (Có hậu tố tên container dạng local/dev).*
*   **Bước 3: Nạp dữ liệu cấu trúc mẫu (Seed Data)**
    Do môi trường phát triển cần có sẵn dữ liệu để kiểm thử tính đúng đắn của code, lập trình viên tiến hành chạy script nạp nhanh cơ sở dữ liệu:
    ```bash
    bash import_db.sh
    ```
    Sau đó, sử dụng MongoDB Compass kết nối trực tiếp qua cổng công khai `27017` để kiểm tra các bộ sưu tập dữ liệu.
*   **Bước 4: Kiểm thử luồng nghiệp vụ cục bộ**
    1.  Truy cập giao diện Front-end qua cổng phát triển: `http://localhost:8082`.
    2.  Đăng nhập với tài khoản mẫu (NV-0001 / Votienkhoa123@) để xác thực tính năng hot-reload và kết nối API nội bộ.

### 6.2. PHẦN 2: HƯỚNG DẪN TRIỂN KHAI TRÊN MÔI TRƯỜNG KIỂM THỬ TÍCH HỢP (UAT)
Môi trường UAT được triển khai trên máy chủ ảo Staging VPS nhằm mục đích giúp đội ngũ QC (Quality Control) hoặc khách hàng kiểm thử diện rộng các tính năng trước khi bàn giao.

*   **Bước 1: Quy hoạch cấu trúc tệp tin trên Staging VPS**
    Trên máy chủ VPS, tạo thư mục biệt lập `/opt/pharmacy-uat/` và chuẩn bị các file cấu hình cần thiết bao gồm: `.env.uat`, `nginx.uat.conf`, và `docker-compose.uat.yml`. Tuyệt đối không chứa thư mục mã nguồn gốc tại đây.
*   **Bước 2: Khởi dựng hệ thống bằng Docker Image đóng gói sẵn**
    Tải các bản build image an toàn đã được đóng gói sẵn từ Docker Registry và khởi chạy thông qua lệnh:
    ```bash
    sudo docker compose -f docker-compose.yml -f docker-compose.uat.yml --env-file .env.uat up -d
    ```
*   **Bước 3: Cấu hình phân quyền truy cập HTTP Basic Auth**
    Để bảo mật môi trường thử nghiệm khỏi người ngoài, truy cập vào container Nginx UAT để tạo file chứa thông tin tài khoản được phép vào hệ thống:
    ```bash
    sudo docker exec -it pharmacy-frontend-uat htpasswd -c /etc/nginx/.htpasswd uat_user
    ```
*   **Bước 4: Nghiệm thu và Xác thực kiểm thử**
    1.  Truy cập qua tên miền nội bộ hoặc cổng kiểm thử: `http://<IP_Staging_VPS>:8080`.
    2.  Trình duyệt sẽ hiển thị một hộp thoại yêu cầu nhập tài khoản `uat_user` trước khi cho phép tiếp cận giao diện đăng nhập chính thức của nhà thuốc.
    > 📷 **[HÌNH 3]**: *Ảnh chụp màn hình hộp thoại đăng nhập bảo vệ HTTP Basic Authentication xuất hiện trên trình duyệt web khi truy cập môi trường UAT.*

### 6.3. PHẦN 3: HƯỚNG DẪN TRIỂN KHAI TRÊN MÔI TRƯỜNG VẬN HÀNH CHÍNH THỨC (PRODUCTION)
Môi trường tối cao đòi hỏi tính ổn định tuyệt đối, bảo mật đa tầng, giới hạn cứng tài nguyên phần cứng để chống treo server và bắt buộc mã hóa HTTPS.

*   **Bước 1: Thiết lập chứng chỉ bảo mật SSL và Phân vùng lưu trữ đĩa cứng**
    1.  Tạo thư mục cấu trúc lưu trữ bảo mật trên live server tại đường dẫn `/app/pharmacy-prod/ssl/`.
    2.  Di chuyển các file chứng chỉ số thương mại hợp pháp (`duocankhang.crt` và `duocankhang.key`) vào thư mục trên.
    3.  Khởi tạo phân vùng đĩa cứng vật lý `/var/lib/pharmacy/mongodb-data` dành riêng cho việc lưu trữ tệp tin dữ liệu bền vững của MongoDB.
*   **Bước 2: Triển khai thắt chặt an ninh và Khống chế tài nguyên**
    Sử dụng file override production để áp dụng các chính sách giới hạn tài nguyên CPU/RAM, kích hoạt log rotation xoay vòng chống tràn dung lượng ổ cứng, đồng thời đóng kín hoàn toàn các cổng database:
    ```bash
    sudo docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env.prod up -d
    ```
    > 📷 **[HÌNH 4]**: *Ảnh chụp màn hình Terminal chạy lệnh `sudo docker ps` trên môi trường Production, chứng minh các cổng 8081 (Backend) và 27017 (MongoDB) hoàn toàn không được map ra ngoài, chỉ có cổng 80 và 443 của Nginx mở ra Internet.*
*   **Bước 3: Kiểm tra trạng thái chịu tải và Sức khỏe Container**
    Thực hiện lệnh giám sát thời gian thực để theo dõi tỷ lệ tiêu thụ tài nguyên của hệ thống live:
    ```bash
    sudo docker stats
    ```
    Đảm bảo lượng RAM và CPU tiêu thụ của các container `frontend`, `spring-boot`, `mongodb` luôn nằm trong ngưỡng giới hạn an toàn đã cấu hình ở Chương 5.
*   **Bước 4: Nghiệm thu luồng hoạt động an toàn khép kín**
    1.  Người dùng cuối truy cập qua tên miền chính thức: `https://duocankhang.vn`.
    2.  Kiểm tra biểu tượng ổ khóa an toàn (SSL/TLS) trên thanh địa chỉ của trình duyệt để đảm bảo luồng truyền tải dữ liệu đã được mã hóa.
    3.  Thực hiện thao tác bán hàng thực tế và kiểm tra biểu đồ phân tích xu hướng tại phân hệ báo cáo để đảm bảo dữ liệu ghi nhận xuống đĩa cứng máy chủ Production hoàn toàn chính xác.
    > 📷 **[HÌNH 5]**: *Ảnh chụp màn hình giao diện hệ thống Dược An Khang chạy thực tế trên môi trường Production với tên miền có giao thức HTTPS an toàn.*
